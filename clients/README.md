# `clients/` — generated backend SDKs

Python and Go clients for the chat-service REST API, generated from
[`openapi/chat-api.yaml`](../openapi/chat-api.yaml).

- [`python/`](python/) — `dhaam-ccrm-chat`, generated by **openapi-python-client**
- [`go/`](go/) — `github.com/dhaamai/chat-sdk/clients/go`, generated by **ogen**

Per PRD §5, backend SDKs are generated, not hand-written: *"Hand-maintaining
five backend SDKs is how teams end up with five subtly different behaviors on
the same endpoint."* `@dhaam-ccrm/node` is the deliberate exception — the
hand-written ergonomic layer that holds the secret key, mints tokens and
verifies webhook signatures. Nothing in this directory competes with it.

```bash
make generate     # regenerate both clients from the spec
make check        # fast drift check — hashes only, no toolchain
make check-full   # regenerate into a temp dir and diff byte-for-byte
make test         # Go + Python client tests
```

Neither generator needs Java or Docker. `generate` needs Go and Python 3.

---

## Which generator, and why

The spec is **OpenAPI 3.1**, and it uses 3.1 in earnest: `type: [string,
"null"]` unions, `oneOf: [$ref, {type: "null"}]`, `const`,
`contentEncoding: binary`, and a top-level `webhooks:` block. That eliminated
most of the field before quality was even a question.

### Go: `ogen` v1.24.0 — pure Go, 3.1-native

`go run github.com/ogen-go/ogen/cmd/ogen@v1.24.0`. No Java, no Docker,
nothing on PATH that Go does not already put there.

**`oapi-codegen` was tried first and cannot read this spec.** It prints

> WARNING: You are using an OpenAPI 3.1.x specification, which is not yet
> supported by oapi-codegen … it is recommended to downgrade your spec to 3.0.x

and then fails outright:

> error converting Schema ChatMessage to Go type: error generating Go schema
> for property 'attachment': error generating type for oneOf: error resolving
> primitive type: unhandled Schema type: &[null]

Downgrading the spec is not on the table — it is the source of truth and it is
not ours to edit.

**`openapi-generator` (Java) 7.18.0 is worse than it looks.** It runs, warns
that "OpenAPI 3.1 support is still in beta", throws two
`NullPointerException`s inside its own OpenAPI Normalizer, and **carries on
and emits a client anyway**. With `enumClassPrefix=true` that client compiles.
It is also missing **six of the eight operations**:

```
$ grep -h 'func (a \*[A-Za-z]*APIService)' api_*.go | sort -u
MintToken(  MintTokenExecute(
UploadSessionAttachment(  UploadSessionAttachmentExecute(
WebhookMessageCreated(  …  WebhookTicketLinked(
```

`listSessions`, `createSession`, `getSessionFull`, `listSessionMessages`,
`closeSession` and `reopenSession` are gone. The cause is in its own log:

> Duplicate file path detected … path=…/api_sessions.go

The three webhook operations are tagged `Sessions`, so they generate to
`api_sessions.go` — the same file as the six real session operations — and the
second write wins. The result compiles, ships six methods that POST webhooks
*to* a customer's receiver (backwards), and silently lacks every session read.
A generator that produces a plausible, compiling, wrong client is the worst
outcome available here, and it costs a JDK in CI to get it.

Without the 3.1 problem `oapi-codegen` would be the lighter choice: ogen's
runtime pulls **17 indirect modules** into a consumer's graph (`zap`,
`yaml.v2`, `uuid`, `regexp2`, `decimal`, `x/net`, `x/text`, `x/exp`) because
its generated validators import `ogen/validate` → `ogen/jsonschema`. That is
the real cost of this choice and it is worth revisiting if oapi-codegen ever
[supports 3.1](https://github.com/oapi-codegen/oapi-codegen/issues/373).
ogen also sets the floor at **Go 1.25** — its own `go` directive, not ours.

In exchange, ogen produces the only Go client of the three that is actually
correct about this spec: distinct `Opt*` and `OptNil*` types for
absent-vs-null, a sum type per operation covering every documented status, and
per-operation security that sends `Authorization` **and** `X-Publishable-Key`
exactly where the spec's `security` blocks say to.

### Python: `openapi-python-client` 0.26.1 — pure Python, 3.1-native

`pip install openapi-python-client==0.26.1`. Generates this spec with **zero
warnings**. Output is `httpx` + `attrs`, fully annotated, and models
absent-vs-null honestly (`Union[None, Unset, str]`). Runtime dependencies are
`httpx`, `attrs`, `python-dateutil` — nothing else.

One caveat, pinned by a test rather than buried here: it models a **single**
credential (`AuthenticatedClient.token`) and ignores the `apiKey` security
scheme, so `X-Publishable-Key` is not sent automatically. See
[`python/README.md`](python/README.md).

`ruff` is pinned exactly (0.13.3) even though it is only a formatter: the
generator shells out to it, so its output *is* the committed bytes.
openapi-python-client declares it as `ruff<0.14,>=0.2`, and ruff 0.14 does not
merely reformat — it fails the generator outright on `UP007`.

## Checked in, not generated on demand

The generated trees are committed: 13 Go files (~15.4k lines) and 54 Python
files (~5.5k lines).

The decisive reason is Go. `go get` has no code-generation step; a consumer
cannot run a generator, so a Go module that is not in the repository does not
exist. Beyond that:

- **CI stays hermetic.** The main `verify` job installs Node and nothing else.
  A `clients` job that only runs when `openapi/` or `clients/` changed is the
  only place Go and Python are needed.
- **Nobody debugs a generator on a Friday.** A generation step in the build is
  a network dependency and a version-skew surface on every checkout.
- **Diffs are readable.** A spec change and its blast radius across two
  languages land in one reviewable commit.

The cost is review noise. [`.gitattributes`](.gitattributes) marks both trees
`linguist-generated=true`, so GitHub collapses them by default and keeps them
out of language stats. Every file also carries a `Code generated … DO NOT
EDIT.` header.

## How regeneration stays honest

A generated client that has quietly drifted from the spec is worse than no
client at all — it is wrong with the authority of something that looks
machine-checked. Two gates, because they catch different things at different
prices.

### Fast — `make check`

Shell and `shasum`. No Go, no Python, no network. Compares
[`generated.lock`](generated.lock) against reality:

| Recorded | Fails when |
|---|---|
| sha256 of `openapi/chat-api.yaml` | the spec changed and nobody regenerated |
| pinned generator versions | `versions.env` moved and nobody regenerated |
| a digest over each generated tree's contents **and layout** | generated code was hand-edited, or a file added or deleted |

Cheap enough to run unconditionally on every PR.

### Full — `make check-full`

Regenerates both clients into a temp directory with the pinned generators and
diffs byte-for-byte. Takes a few seconds once the module and pip caches are
warm; needs Go and Python.

This is the only gate that proves the committed code is what the generators
emit. Fast mode can be defeated by editing a generated file *and* rerunning
`write-lock.sh`; full mode cannot. Run it whenever `openapi/` or `clients/`
changed — see [`ci/clients.yml`](ci/clients.yml).

### The base path is derived, not remembered

The spec's `servers` block resolves to `{apiUrl}/chat-services/api/v1`. **It
once said `{apiUrl}/v1`, which no route serves.** Neither generator protects
you from that: ogen's `NewClient` takes a server URL and
openapi-python-client's `Client` takes `base_url`, and neither consults
`servers` at all. A client generated from the wrong spec would have compiled,
type-checked, imported cleanly and 404'd on every call.

So the base path is not left to a README.
[`scripts/emit_base_path.py`](scripts/emit_base_path.py) parses the `servers`
block during generation and emits it as source in both clients —
`chatapi.BasePath` / `chatapi.ResolveBaseURL`, `BASE_PATH` /
`resolve_base_url`. The script is strict: more than one server, a URL that
does not start with `{apiUrl}`, an undeclared variable or a templated path is
an error, not a guess.

Both test suites then assert on the literal path that leaves the client, and
both were confirmed to fail when `BasePath` is set back to `/v1`.

**Both clients were exercised live** against a chat-service on `:3000` with
the demo keys, and each minted a real 3600-second JWT from
`http://localhost:3000/chat-services/api/v1/tokens`. Re-run with:

```bash
set -a; . examples/demo/.env; set +a
CHAT_LIVE_API_URL="$CHAT_API_URL" CHAT_LIVE_SECRET_KEY="$CHAT_SECRET_KEY" \
  make -C clients test
```

The live checks skip themselves when those variables are absent, so CI does
not need a backend.

## What you still have to write

These clients are HTTP plumbing. They are deliberately **not** an SDK.
Everything below is out of scope on purpose — it is `@dhaam-ccrm/node`'s job,
or yours.

| Not provided | What you must do |
|---|---|
| **Auth helpers.** Go declares `SecuritySource` and never implements it; Python takes one `token` and no publishable key. | Implement `SecuritySource` (Go) or pass `token=` plus a `X-Publishable-Key` constructor header (Python). See each language's README. |
| **Token minting as a flow.** `POST /tokens` is generated; deciding *when* to mint, caching, and refreshing on `AUTH_EXPIRED` are not. | Call `MintToken` from your own backend endpoint, cache by user, and re-mint before `expiresIn` elapses. Never ship the secret key to a browser. |
| **Webhook signature verification.** `X-ChatSDK-Signature` is `t=<unix>,v1=<hmac-sha256>` over `${t}.${rawBody}`, keyed with the secret key. | Verify it yourself with a constant-time compare over the **raw, unparsed** body, and reject a `t` more than 5 minutes off. `@dhaam-ccrm/node` implements this so JS consumers never hand-roll it; Python and Go consumers must. The `Webhook*Event` body types *are* generated, so decoding an already-verified body is typed. |
| **Webhook receivers.** Both generators can emit a webhook server. Both are switched off. | Route the four events yourself. A generated receiver would decode `X-ChatSDK-Signature` as an ordinary header and hand the body to a handler with no verification anywhere in the path — a complete-looking webhook endpoint that authenticates nobody. |
| **Pagination iterators.** `listSessionMessages` returns `messages` + `hasMore`; the cursor is a message id you pass as `before`. | Loop yourself: take the oldest id from the page and pass it as `before` until `hasMore` is false. |
| **Retries and backoff.** `RATE_LIMITED` carries `Retry-After`; `INTERNAL` carries an authoritative `retryable`. | Wrap the client's `http.Client` (Go) or pass `httpx_args` (Python). Branch on `error.code`, never on `message`. |
| **Idempotency keys.** The header is a generated parameter; generating and reusing a key across a retry is not. | Generate a UUID per logical operation and reuse it for every retry of that operation, for 24h. |
| **Anything WebSocket.** No frames, no `message.markRead`, no presence. | These clients are request/response only. Advancing a read watermark is WS-only by design (PRD §9.5) — there is no REST endpoint for it and its absence is not an oversight. |

## Bumping a generator

1. Edit [`scripts/versions.env`](scripts/versions.env).
2. `make generate`
3. Review the diff, run `make test`, commit **the regenerated tree and the
   lockfile in the same commit**.

`make check` fails on step 2 being skipped, which is the point.

## Layout

```
clients/
├── Makefile
├── generated.lock              digests the drift check compares against
├── ci/clients.yml              CI job — NOT YET WIRED IN, see below
├── scripts/
│   ├── versions.env            pinned generator versions
│   ├── generate.sh             regenerate both clients
│   ├── check-drift.sh          the two gates
│   ├── write-lock.sh           rewrite generated.lock (called by generate.sh)
│   ├── emit_base_path.py       servers block -> source, in both languages
│   ├── test_emit_base_path.py  its tests
│   └── lib.sh
├── go/
│   ├── ogen.yml                generator config, with the reasoning
│   ├── chatapi/                GENERATED — do not edit
│   └── tests/                  what the generator cannot check
└── python/
    ├── openapi-python-client.yml
    ├── pyproject.toml          hand-written; --meta none emits no packaging
    ├── dhaam_ccrm_chat/        GENERATED — do not edit
    └── tests/
```

> **`ci/clients.yml` is not wired into `.github/workflows/` yet.** That
> directory was outside this change's ownership. Until someone adds the job,
> the drift gates only run when a human runs them — which is exactly the
> failure mode they exist to prevent. See [`ci/README.md`](ci/README.md).
