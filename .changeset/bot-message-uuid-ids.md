Accept server-minted UUID message ids on `message.new`.

`message.new.d.id` was validated as a ULID. That holds for client-originated
messages — the id on the wire IS the ULID the client put on its own
`message.send` envelope — but not for messages the backend mints itself. Bot
replies and system messages never pass through a client envelope and carry the
database's UUID default instead.

Two consequences, both observed against a live chat-service-node:

- every AI bot reply was dropped at the transport with
  `d.id must be a valid ULID`, so a bot-mode session looked silent;
- `connection.ack.d.replay` validates each entry as a whole frame and fails the
  entire ack on any one bad entry, so a session whose replay window contained a
  single bot message could not complete a resume handshake at all.

`message.new.d.id` now accepts a ULID or a UUID, via the new exported
`isValidMessageId` guard. Envelope frame ids and `ack.ref` stay strict ULID —
those are generated by the client and by the server's own frame builder, where
§7.2 holds.
